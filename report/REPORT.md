## 0. 3분 요약

**만든 것**
사용자가 질문하면 인공지능기본법 조문을 찾아 **근거와 함께 답하는 API** (`POST /ask` → `{answer, sources}`).

**핵심 결과**

| 무엇을 쟀나 | 결과 |
|---|---|
| 검색이 정답 조문을 1등으로 가져오는 비율 (Hit@1) | 기본 검색 **0.69** → 최종 **0.87** |
| 정답이 평균 몇 등에 나오나 (MRR) | 기본 **0.78** → 최종 **0.92** |
| 상위 5개 안에 정답이 있는 비율 (Hit@5) | 기본 0.91 → 최종 **1.00** |
| 답변이 정답 근거와 맞는 비율 (정답성) | **0.84** (64문항) |
| 법에 없는 질문 10개를 "확인되지 않는다"고 거절 | **10/10** |
| 본문에 없는 내용을 지어낸 답변 (환각) | **5%** (64문항 중 3개) |

**가장 중요한 발견 3가지**

1. 검색을 좋게 만든 건 **Multi Query가 아니라 Reranker**였다. Multi Query 단독은 오히려 순위를 흩뜨렸고, Reranker와 합쳤을 때 효과가 났다.
2. 검색이 잘 되어도 **답변이 틀리는 구간이 따로 있다.** 과태료·벌칙 질문(의무·벌칙형)과 여러 조문에 퍼진 질문(주제형)이 약하다.
3. 지표 하나만 보면 **실패가 가려진다.** 조문 단위 Hit은 "제2조를 찾았다"로 세지만, 실제로는 엉뚱한 호를 가져온 경우가 있었다. 그래서 청크 단위(Chunk@K)와 Recall을 함께 봤다.

**아직 못한 것**: 골든셋을 사람이 전부 검토하지 못했고, 개선 아이디어(8장)는 구현하지 않았다. 점수는 낙관적일 수 있다(9장).

## 1. 전체 구조

질문이 들어와서 답이 나가기까지의 흐름이다.

```
[미리 해 두는 작업: Offline]

 법령 파일  →  구조 읽기  →  청크로 나누기  →  임베딩  →  Qdrant 저장
 (XML)        (장·조·항·호)   (62개)          (벡터)


[질문이 올 때: Online]

 질문
  ↓
 ① Multi Query    질문을 법률 용어로 3개 더 바꿔 쓴다 (총 4개)
  ↓
 ② Dense 검색     4개 질문으로 각각 검색해 RRF로 합친다 → 후보 20개
  ↓
 ③ Reranker       LLM이 후보 20개를 0~10점으로 채점해 다시 줄 세운다
  ↓
 ④ 상위 5개       LLM에게 근거 본문으로 준다
  ↓
 ⑤ 근거 기반 답변  본문에 있는 내용만, 조문 번호를 밝히며 답한다
```

## 2. 용어 먼저

| 용어 | 한 줄 설명 |
|---|---|
| **청크** | 검색하는 단위로 잘라 둔 문서 조각 |
| **임베딩** | 글을 숫자 벡터로 바꾼 것. 뜻이 비슷하면 벡터도 가깝다 |
| **Dense 검색** | 벡터가 가까운 청크를 찾는 방식 |
| **Multi Query** | 질문을 여러 표현으로 바꿔 검색하는 방식 |
| **RRF** | 여러 검색 결과의 순위를 하나로 합치는 방법 |
| **Reranker** | 검색된 후보를 질문과의 관련도로 다시 줄 세우는 단계 |
| **골든셋** | 질문과 정답을 미리 만들어 둔 시험지 |
| **Hit@K** | 상위 K개 안에 정답이 **하나라도** 있는 비율 |
| **Recall@K** | 정답이 여러 개일 때, 상위 K개에서 **몇 개나** 찾았는지 |
| **MRR** | 정답이 처음 나온 순위의 역수를 평균한 값. 1.0이면 항상 1등 |
| **Chunk@K** | 조문이 아니라 **정답 청크** 단위로 센 Hit@K |

## 3. 핵심 기능 1: 문서 읽기

**하는 일**: 법령 파일에서 장·절·조·항·호·목 구조를 뽑아낸다. 이게 틀어지면 뒤의 모든 단계가 흔들린다.

**선택한 방식**

| 형식 | 장점 | 단점 | 역할 |
|---|---|---|---|
| 법제처 XML | 구조가 태그로 나뉘어 있어 가장 정확 | Open API 신청이 필요 | **실제 적재 입력**이자 정답지 |
| HWPX | 번호와 문단이 글자로 그대로 들어 있음 | 파서를 직접 짜야 함 | 담당 구현 (검증 완료) |
| PDF + Docling | 과제 요구와 일치 | 레이아웃에서 구조를 **추정**해야 함 | 팀원 진행 중 |

**어떻게 골랐나**: 형식마다 구조의 정확도가 다르므로, **XML을 정답지로 두고 다른 로더가 얼마나 같은 결과를 내는지 채점**하는 방식으로 정했다. 세 로더 모두 같은 `Law` 트리를 돌려주기 때문에 이후 단계는 어떤 로더를 쓰든 그대로다.

**HWPX 로더 검증 결과** (XML 대비)

| 항목 | 결과 |
|---|---|
| 조문 / 항 / 호 / 목 개수 (46 / 166 / 191 / 13) | 일치 |
| 조문 본문 글자 | 46/46 완전 일치 |
| 청킹 결과 | **62/62 완전 일치** |

일치시키려고 파서가 처리한 것은 4가지다: 조 제목에 붙은 첫 항 분리, 개정 표기 제거, 따옴표 통일, 머리글·바닥글 무시.

**주의**: 실제 평가는 모두 **XML로 적재한 데이터** 기준이다. PDF(Docling) 비교는 아직 못 했다.

## 4. 핵심 기능 2: 청킹 (문서 자르기)

**원칙**: 법은 "조"가 의미 단위이므로 **조 1개 = 청크 1개**가 기본이다. 필요한 곳만 더 잘게 자른다.

| 대상 | 자르는 방식 | 이유 |
|---|---|---|
| 일반 조 | 조 1개 = 청크 1개 | 답변의 출처("제○조")와 1:1로 맞는다 |
| 제2조(정의) | **호 1개 = 청크 1개** | 정의 12개가 한 청크에 섞이면 "고영향 인공지능이란?" 같은 질문에 약하다 |
| 1000자 넘는 조 | 항 경계를 지키며 분할 | 항 중간에서 자르면 의미가 깨진다 |
| 부칙 | 시행일이 있는 2건만 | 정부조직법 개정 같은 무관한 부칙은 제외 |

**모든 청크 앞에 경로를 붙인다**: `[… > 제3장 … > 제17조의2(제목)]`. 어느 장·절 소속인지도 검색에 반영하려는 것이다.

**결과**: 조문 46개 → 청크 62개 (길이 최소 75자 / 중앙 368자 / 최대 956자).

**버린 대안**
- 항 단위로 전부 분할: 짧은 항은 "제1항에 따른…"처럼 단독으로 뜻이 불분명하다.
- 고정 길이 분할: 조문 중간이 잘리고 출처가 사라진다.

**측정은 못 했다**: "정의형은 호 단위 분할 덕에 Hit@3이 1.00"이라고 말할 수는 있지만, 분할하지 않은 경우와 직접 비교하지는 않았다. 효과가 있는 것처럼 보일 뿐 입증된 것은 아니다.

## 5. 핵심 기능 3: 검색 (가장 많이 실험한 부분)

### 5.1 어떻게 실험했나

한 번에 다 넣지 않고 **한 가지씩 추가하며 같은 골든셋으로 비교**했다. 효과가 수치로 확인된 것만 남기기 위해서다.

| 단계 | 구성 | 보려던 것 |
|---|---|---|
| R0 | Dense 검색만 | 기준선 |
| R1 | + Multi Query | 일상어 질문이 좋아지는가 |
| R2 | + Reranker | 순위가 바로잡히는가 |

**Hybrid(BM25) 검색은 하지 않기로 했다.** 한국어는 조사 때문에 형태소 분석이 필요해 구현 부담이 컸고, 대신 Multi Query와 Reranker를 비교하는 쪽으로 정했다.

**임베딩은 `text-embedding-3-small`로 고정했다.** 검색 방식만 바꿔야 성능 차이의 원인이 분명해지기 때문이다.

### 5.2 결과

전체 (근거가 있는 질문 54개)

| 구성 | Hit@1 | Hit@3 | Hit@5 | Recall@5 | MRR | Chunk@1 |
|---|---|---|---|---|---|---|
| R0 Dense | 0.69 | 0.83 | 0.91 | 0.83 | 0.78 | 0.77 |
| R1 + Multi Query | 0.61 | 0.85 | 0.93 | 0.84 | 0.75 | 0.69 |
| **R2 + Reranker** | **0.87** | **0.96** | **1.00** | **0.94** | **0.92** | **0.92** |

유형별 Hit@1 / MRR

| 유형 | n | R0 | R1 | R2 |
|---|---|---|---|---|
| 정의형 | 8 | 0.88 / 0.92 | 0.88 / 0.94 | 0.88 / 0.90 |
| 조문번호형 | 8 | 0.62 / 0.73 | 0.50 / 0.64 | 0.50 / 0.75 |
| 구어체 | 10 | 0.50 / 0.63 | 0.50 / 0.75 | **1.00 / 1.00** |
| 의무·벌칙형 | 8 | 0.62 / 0.78 | 0.62 / 0.77 | **1.00 / 1.00** |
| 정책·기관형 | 8 | 0.88 / 0.94 | 0.75 / 0.88 | **1.00 / 1.00** |
| 주제형 | 8 | 0.50 / 0.59 | 0.50 / 0.58 | 0.75 / 0.84 |
| 시행일 | 4 | 1.00 / 1.00 | 0.50 / 0.66 | **1.00 / 1.00** |

Chunk@K는 정답 청크가 지정된 문항만 센다 (정의형 8, 시행일 4, 구어체 1 = 13문항).

| 유형 | n | R0 | R1 | R2 |
|---|---|---|---|---|
| 정의형 | 8 | 0.88 / 0.88 | 0.88 / 0.88 | 0.88 / 0.88 |

### 5.3 각 단계를 어떻게 해석했나

**R1 (Multi Query): 효과가 엇갈렸다**
- 일상어 질문은 확실히 좋아졌다. 구어체 Hit@3이 0.70 → 1.00.
- 하지만 시행일(Hit@1 1.00 → 0.50)과 조문번호형은 나빠졌다. 질문을 바꿔 쓰면서 원래 질문의 정확한 표현("제17조의2" 등)이 희석된 것으로 보이나, 원인을 직접 확인하지는 않았다.
- 질문별로 좋아진 것 9개, 나빠진 것 10개. 54문항에서 ±0.07은 질문 4개 차이라 **우연과 구분하기 어렵다.**
- 정리: 정답을 후보 안에 **넣어 주는** 효과는 있지만 **순위는 흩뜨린다.**

**R2 (Reranker): 결정적으로 좋아졌다**
- R1 대비 순위가 좋아진 질문 18개, 나빠진 질문 1개(q01), 그대로 35개. 방향이 일관되어 우연으로 보기 어렵다.
- 기준선(R0) 대비로는 좋아진 질문 15개, 나빠진 질문 4개, 그대로 35개다 (`eval.compare_runs r0_dense r2_rerank`).
  - 좋아진 15개: 구어체 5개(q17, q19, q22, q23, q26), 의무·벌칙형 3개(q30~q32), 조문번호형 3개(q09, q10, q14), 주제형 3개(q45, q46, q48), 정책·기관형 1개(q40)
  - 나빠진 4개: q01(3위→5위), q12·q13(1위→2위), q47(3위→5위). q12·q13은 조문번호형 동점 문제(아래 ②)와 같은 유형이다.
- R1이 후보를 넓히고, R2가 그 후보를 정리하는 **역할 분담**이다. R1만으로는 R0보다 못해 보였던 것이 R2에서 보상된다.
- 단, "R0에 R2만 붙인 구성"은 측정하지 않았다. 그래서 **R1이 꼭 필요했는지는 이 실험으로 답할 수 없다.**

### 5.4 지표 하나만 보면 놓치는 것

**① 정의형 q01 ("고영향 인공지능이란?")**
- 조문 단위 Hit은 제2조의 다른 호가 나와도 "제2조를 찾았다"고 센다. 그래서 R0 → R1에서 순위가 올라 "개선"으로 집계됐다.
- 하지만 실제 답변은 정의를 말하지 못했다. 청크 단위로 보면 R1은 오히려 R0보다 낮았다(0.77 → 0.69).
- R2로도 못 고친다. 정답 청크(`제2조#제4호`)가 후보 20개에 아예 없었기 때문이다. 없는 후보는 재정렬로 끌어올릴 수 없다.

**② 조문번호형 ("제31조는?")**
- Hit@3은 1.00인데 Hit@1은 0.50이다. 제31조를 **언급만 한** 다른 조문이 정답과 같은 10점을 받아 동점이 되기 때문이다. 이 문제는 "제○조" 정규식 + 메타데이터 필터가 맞는 처방이라 아직 구현하지 않았다.

**③ 의무·벌칙형**
- Hit@1은 1.00인데 Recall@5는 0.88이다. 정답이 여러 조문인 질문에서 일부를 놓친다는 뜻이다. 6.3절에서 다시 다룬다.

## 6. 핵심 기능 4: 답변 생성과 평가

### 6.1 답변 생성 ([rag/pipeline.py](rag/pipeline.py))

상위 5개 청크를 근거 본문으로 주고, 다음 규칙을 프롬프트에 고정했다.

- 본문에 있는 내용만 근거로 답하고, 일반 지식으로 보충하지 않는다.
- 답변 안에서 "제34조 제1항"처럼 근거 조문을 밝힌다.
- 근거가 없으면 "제공된 법령 본문에서는 확인되지 않습니다."라고만 답하고, 관련 있어 보이는 조문은 한 줄로 알려 준다.
- 시행령에 위임된 내용은 "대통령령으로 정한다"까지만 말한다.

### 6.2 어떻게 평가했나

검색 평가와 답변 평가를 **따로** 쟀다. 검색이 좋아도 답변이 틀릴 수 있고, 반대도 가능해서 문제가 어느 단계에 있는지 가려내려는 것이다.

| 구분 | 방법 | 보는 것 |
|---|---|---|
| 코드가 확인 | 답변에 정답 조문 번호가 들어 있는가 | 조문 인용 |
| 코드가 확인 | "확인되지 않"이라는 문구가 있는가 | 거절 동작 |
| LLM이 채점 | 정답 근거와 답변을 비교 | **정답성** |
| LLM이 채점 | 질문에 대한 답인가 | **관련성** |
| LLM이 채점 | 답변의 주장이 검색된 본문에서 확인되는가 | **근거 충실성** |
| LLM이 채점 | 본문에 없는 사실을 말했는가 | **환각** (낮을수록 좋음) |

**"법에 없음" 10개를 따로 둔 이유**: 정답이 없는 질문에서 억지로 답하는지(환각)를 보려는 것이다. 이 10개에는 일부러 **근접 오답**(원문에 관련 단어는 있지만 답은 없음) 4개를 넣었다. 단어가 아예 없는 질문만 넣으면 검색이 엉뚱한 곳으로 가서 쉽게 거절되고, 그러면 환각 방지 점수가 부풀기 때문이다.

### 6.3 결과 (64문항)

| 유형 | n | 정답성 | 관련성 | 충실성 | 환각 | 조문인용 | 오거절 |
|---|---|---|---|---|---|---|---|
| 정의형 | 8 | 0.88 | 1.00 | 1.00 | 0.00 | 0.88 | 0.12 |
| 조문번호형 | 8 | 1.00 | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 |
| 구어체 | 10 | 1.00 | 1.00 | 1.00 | 0.00 | 1.00 | 0.10 |
| 의무·벌칙형 | 8 | **0.62** | 1.00 | 1.00 | 0.00 | 1.00 | 0.62 |
| 정책·기관형 | 8 | 0.88 | 1.00 | 0.88 | 0.12 | 1.00 | 0.00 |
| 주제형 | 8 | **0.50** | 1.00 | 1.00 | 0.12 | 1.00 | 0.12 |
| 시행일 | 4 | 1.00 | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 |
| 법에 없음 | 10 | 0.90 | 1.00 | 0.90 | 0.10 | - | 올바른 거절 1.00 |
| **전체** | 64 | **0.84** | 1.00 | 0.97 | 0.05 | 0.98 | 0.15 |

**잘된 점**
- 조문번호형·구어체·시행일은 정답성 1.00. 검색 R2의 개선이 답변까지 이어졌다.
- 법에 없는 질문 10개를 **전부 거절**했다. 근접 오답 4개(q60~q63)도 억지로 답하지 않았다.

**약한 곳과 그 원인**

*의무·벌칙형 (정답성 0.62)*: 문제 문항은 q31, q32, q33이고 모두 **과태료 조문(제43조)을 연결하지 못했다.**

- 제43조는 "제31조제1항을 위반하여 고지를 이행하지 아니한 자"처럼 **다른 조문 번호만 나열한 목록형 조문**이다. 질문의 "알리지 않으면", "대리인을 지정하지 않으면" 같은 표현과 문장이 겹치지 않아 검색이 잡기 어렵다.
- q31, q33은 상위 5개에 제43조가 없었다. 의무 조문만 가져와 "과태료는 확인되지 않는다"고 답했다.
- q32는 제43조가 2위로 들어왔는데도 답변이 연결하지 못했다. 이건 검색이 아니라 **답변 생성** 쪽 문제로 보인다.
- 조문 단위 Hit@1은 이 셋 모두 1.0이라 **Hit만 봤으면 드러나지 않았을 실패**다. Recall@5(0.5)에서 보였다.

*오거절 0.62는 과대 집계다.* 오거절로 센 5건 중 q27과 q34는 정답 조문(제35조)을 제대로 찾았고, 답변도 "반드시 해야 한다고까지는 확인되지 않고 노력하여야 한다"는 취지로 원문과 맞는 것으로 보인다. "확인되지 않"이라는 문구가 답변 **어디에든** 있으면 거절로 세는 규칙 때문에 이렇게 집계됐다. 실제 오거절에 가까운 건 q31, q33 두 건이다.

*주제형 (정답성 0.50)*: 정답이 여러 조문에 퍼진 질문이라 일부만 짚거나 범위 밖 조문을 섞었다. 검색 단계에서도 가장 약했던 유형이다.

*환각 3건* (64문항 중 3개, 확인함): q38(정책·기관형), q49(주제형), q59(법에 없음).
- q59는 거절은 했지만 제16조 제4항을 끌어와 해석을 덧붙였다.
- q38은 본문에 없는 조문 인용이 섞였다.
- q49는 정답 범위(제33~35조)를 넘어 제2조 제4호와 제8조까지 포함했다.

## 7. 평가 방법과 골든셋

### 7.1 골든셋 (64문항)

질문 54개는 법에 근거가 있고, 10개는 근거가 없다.

| 유형 | 개수 | 무엇을 보는가 |
|---|---|---|
| 정의형 | 8 | 제2조를 호 단위로 나눈 것이 효과 있는가 |
| 조문번호형 | 8 | "제○조는?" 직접 질의 |
| 구어체 | 10 | 법률 용어 없는 일상어 질문 |
| 의무·벌칙형 | 8 | 의무와 과태료를 잇는 질문 |
| 정책·기관형 | 8 | 위원회·연구소·협회와 지원 정책 |
| 주제형 | 8 | 여러 조문에 퍼진 주제 |
| 시행일 | 4 | 부칙 2건 중 맞는 것 고르기 |
| 법에 없음 | 10 | 근거가 없을 때 거절하는가 |

**채점 기준**: 정답 조문이 여러 개인 문항을 "전부 찾아야 정답"으로 치면 너무 가혹하다. 그래서 Hit은 **하나라도** 찾으면 적중, Recall은 **찾은 비율**로 나눠 셌다.

**버전 동결**: 골든셋을 v1(64문항)으로 확정한 뒤에는 **점수를 보고 정답을 고치지 않기로** 했다. 점수에 맞춰 정답을 바꾸면 평가가 의미를 잃기 때문이다. 원문과 대조해 라벨이 객관적으로 틀렸다고 확인된 경우에만 고치고, 그때는 이력을 남긴다.

### 7.2 그래서 어떤 지표를 쓰나

| 지표 | 역할 |
|---|---|
| Hit@1, MRR | 순위가 얼마나 위에 오는가. 주 지표 |
| Recall@5 | 정답이 여럿인 질문(12문항)에서 얼마나 찾는가 |
| Chunk@K | 조문 단위가 놓치는 실패를 잡는 보조 지표 (13문항) |
| 답변 4개 항목 | 검색과 별개로 답변의 품질을 본다 |

Hit@5는 1.00에 도달해 더는 변별력이 없다. 청크가 62개뿐이라 K가 크면 거의 항상 정답이 포함된다.

## 8. 한계와 다음에 할 일

### 8.1 점수를 읽을 때 주의할 점

1. **같은 골든셋으로 고치고 쟀다.** R2의 채점 규칙(조문번호 우선, 정의 조항 우선)은 R0·R1의 실패 사례를 본 뒤에 썼다. 따로 둔 검증 세트가 없어 **개선폭이 낙관적일 수 있다.**
2. **골든셋을 사람이 전부 검토하지 못했다.** 자동 검사는 "근거 문구가 그 조문에 있다"까지만 보증한다. 특히 해석이 들어간 q34, q60~q63은 사람 검토가 남아 있다.
3. **만든 쪽과 채점하는 쪽이 같은 계열이다.** 골든셋 초안, 재정렬기, 답변 생성, 답변 심판이 모두 LLM이라 점수가 후하게 나올 수 있다. 사람이 샘플을 직접 확인해야 한다.
4. **문항 수가 적다.** 54문항이라 ±0.07은 질문 4개 차이다. 유형별(4~10문항) 수치는 질문 한 개에 크게 흔들린다.
5. **거절 판정이 거칠다.** 6.3절의 오거절 집계처럼, 문구 포함 여부로 거절을 세는 방식이 과대 집계를 만든다.

### 8.2 개선 아이디어 (구현하지 않음)

| 문제 | 아이디어 | 기대 |
|---|---|---|
| 조문번호형 Hit@1 0.50 | 질문에서 "제○조"를 정규식으로 뽑아 메타데이터 필터 적용 | 동점 문제 해결 |
| q01 정의 청크 누락 | 정의 청크 경로 헤더에 용어를 넣기 (`제2조(정의) > 고영향 인공지능`) | 후보에 들어오게 함 |
| 과태료 조문(제43조) 연결 실패 | 제43조 청크에 "과태료, 고지 의무 위반" 같은 설명 헤더 추가, 또는 벌칙 질문일 때 제43조를 함께 검색 | 의무·벌칙형 개선 |
| 오거절 과대 집계 | 문구 포함이 아니라 "답변 전체가 거절인가"로 판정 | 지표 정확도 |
| 점수 낙관 가능성 | 프롬프트를 고치지 않은 별도 질문 세트로 검증 | 신뢰도 |

청크 ID가 그대로면 골든셋 v1은 바뀌지 않지만, 청킹을 바꾸면 R0~R2를 다시 재야 한다.

### 8.3 운영상 알아 둘 점

- **API 호출 한도가 분당 30회**다. 한도에 걸리면 클라이언트가 60초를 쉬고 재시도한다. 처음 `/ask`가 66초 걸린 이유가 이것이었고, 모델 속도 문제가 아니었다.
- 질문 하나에 LLM 호출이 변환·임베딩·재정렬·답변 4번이라, 이 한도에서는 분당 약 7명이 한계다.
- 병렬 호출은 도움이 되지 않고 429 오류만 늘린다.
- 법령이 개정되면 일련번호(MST)가 바뀌므로, 데이터는 버전을 고정한 스냅샷(MST 282791, 법률 제21311호)으로 두고 평가한다.

## 9. 재현 방법

### 9.1 준비 (공통)

```bash
uv sync                                   # 패키지 설치 (.venv 생성)
# 프로젝트 루트에 .env 파일을 만들고 OPENAI_API_KEY=... 를 넣는다
docker compose -f docker-qdrant/docker-compose.yaml up -d   # Qdrant 실행
```

Qdrant는 기본값 `http://localhost:6333`으로 접속한다. 다른 주소를 쓰면 `.env`의 `QDRANT_URL`로 바꾼다. 아래 두 방식은 **실행 방법만 다르고 결과는 같다.**

### 9.2 방법 A: `uv run` (권장)

가상환경을 활성화하지 않아도 `uv`가 `.venv`를 알아서 쓴다. 프로젝트 루트에서 실행한다.

```bash
uv run python -m rag.vectorstore         # 임베딩 후 Qdrant에 저장 (62개 청크)
uv run python -m eval.check_golden_set   # 골든셋 자동 검사
uv run python -m eval.evaluate r0        # 검색 평가 (r0 / r1 / r2)
uv run python -m eval.compare_runs r0_dense r1_multi_query r2_rerank   # 한눈에 비교
uv run python -m eval.evaluate_answers   # 답변 평가 (이어쓰기 가능)
uv run uvicorn app.main:app --reload     # API 서버
```

### 9.3 방법 B: 로컬 호스트 (가상환경 활성화 + localhost 서버)

`uv`를 거치지 않고 가상환경을 직접 켜서 `python`으로 실행한다. 서버는 내 PC의 `localhost`에서 띄우고 접속한다.

```bash
source .venv/bin/activate                # Windows: .venv\Scripts\activate

python -m rag.vectorstore
python -m eval.check_golden_set
python -m eval.evaluate r2
python -m eval.evaluate_answers

uvicorn app.main:app --host 127.0.0.1 --port 8000
```

서버가 뜨면 다음 주소로 확인한다.

| 용도 | 주소 |
|---|---|
| Swagger 문서 (브라우저에서 직접 질문) | http://localhost:8000/docs |
| Qdrant 대시보드 (저장된 청크 확인) | http://localhost:6333/dashboard |

터미널에서 바로 질문해 볼 수도 있다.

```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "고영향 인공지능이란 무엇인가요?"}'
```

`--reload`는 코드를 고치며 개발할 때만 쓰고, 평가를 돌릴 때는 빼는 편이 안전하다.
